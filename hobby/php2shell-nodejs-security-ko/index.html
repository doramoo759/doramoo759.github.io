AI가 찾아낸 PHP2Shell 취약점, PHP·Node.js 업데이트부터 확인하자

Created Date: 2026.10.23 Last Updated: 2026.10.23

Read in English

일본 총리가 AI 로봇에게 도움을 청하는 모습을 상상한 AI 생성 이미지다. 실제 만남이나 발언 장면을 재현한 것이 아니다.

PHP 취약점 소식에 일본 총리까지 사이트 일시 중단을 언급했다. PHP를 오래된 웹사이트에나 쓰는 언어쯤으로 생각했다면, 이번 PHP2Shell은 남의 일로 넘기기 어렵다. 워드프레스의 플러그인을 최신으로 유지해도 그 아래에서 실행되는 PHP 자체가 취약할 수 있기 때문이다.

2026년 10월 23일 기준 우선 확인할 수정 버전은 PHP 8.2.35·8.3.36·8.4.27·8.5.12, Node.js 22.23.4·24.22.1·26.12.1이다. 각 계열에서 이 수정판 이상을 사용하되 배포판의 보안 패치 반영 여부도 함께 확인해야 한다. 아래는 직접 침투시험을 했다는 이야기가 아니라, 공식 공지와 연구 보고서를 비교한 운영자 관점의 정리다. PHP 공식 공지, Node.js 공식 공지

PHP2Shell은 어느 회사가 찾았나: Wiz 한 곳의 이야기는 아니다

이번 이슈의 이름은 PHP2Shell이다. Wiz Research의 공개 보고서는 AI 도구를 활용해 PHP 코어의 문제를 분석하고 실제 애플리케이션에서 인증 없는 원격 코드 실행을 시연했다고 설명한다. 여기서 원격 코드 실행, 즉 RCE는 공격자가 서버에서 자기 코드를 실행하게 만드는 상황을 뜻한다. Wiz 연구 보고서

발견 경로는 한 회사의 단독 성과로 줄이면 부정확하다. PHP 재단은 2024년 Quarkslab 감사와 관련된 문제를 수정하던 중 OOM 문제의 징후를 발견했고, 2026년 8월 11일 Calif가 같은 근본 원인으로 RCE를 보고했다고 밝혔다. OpenAI도 독립적으로 보고했으며 Wiz의 추가 보고는 8월 24일에 들어왔다. 공개된 수정판은 10월 21일 나왔다. PHP 재단의 경위 설명

내가 중요하게 보는 변화는 AI가 버그 이름을 하나 더 찾아냈다는 점보다, 오래되고 다루기 까다로운 문제의 악용 가능성을 입증하는 데 도움이 됐다는 점이다. 이것이 패치를 적용할 수 있는 시간을 더 여유롭게 만들어 주지는 않는다. 방어자도 빨라져야 한다는 쪽에 가깝다.

PHP 프로젝트의 사전 공지는 두 건을 CVSS v4.0 9.2, Critical로 안내했다. PHP-FPM·mod_php·php-cgi 등 웹 요청을 처리하는 구성을 점검 대상으로 보며, 특히 mod_php의 위험을 높게 평가했다. “FPM이니 무관하다”거나 “우리 로그인은 안전하다”는 이유만으로 제외할 문제는 아니다. PHP 보안 권고

다만 취약 버전이 설치돼 있다는 사실과 이미 침해됐다는 사실은 다르다. 공격 경로와 설정, 프로세스 권한에 따라 결과가 달라진다. 웹셸 설치·정보 유출·홈페이지 변조·내부 침투로 이어질 수 있다는 점은 KISA도 경고했다. 서버 프로세스가 읽을 수 있는 비밀값과 접근 가능한 내부 자원이 피해 범위를 가르는 중요한 요소다. KISA 기업 대응 수칙

리눅스 배포판은 취약점 수정만 이전 버전에 반영하는 백포트를 제공할 수 있다. 따라서 버전 문자열이 낮다고 무조건 미수정으로 판정하거나, 자체 컴파일한 최신 PHP를 설치해 놓고 실제 FPM도 바뀌었다고 가정하면 안 된다. PHP를 내장한 NAS·호스팅·어플라이언스는 해당 업체의 CVE 대응 공지가 판단 기준이다.

일본 총리가 “패치가 어렵다면 사이트를 멈추라”고 했나

그런 취지의 요청은 확인된다. J-CAST는 다카이치 사나에 총리가 10월 21일 밤 X에서 공개 웹사이트의 PHP 사용 여부를 확인하고 신속한 패치 적용을 준비해 달라고 요청했다고 보도했다. 즉시 적용하기 어렵다면 웹사이트의 일시 중단도 위험을 줄이는 방법이라는 설명이었다. J-CAST 원문·발언 소개, 10월 22일

출처: J-CAST 뉴스, 2026년 10월 22일 기사의 사진·캡션 영역 캡처(10월 23일). 원문 캡션에 따르면 2026년 9월 자료사진으로, PHP 대응 요청 당시의 현장 사진은 아니다.

이것은 일본의 모든 서버가 침해됐다거나 전국 사이트를 일괄 폐쇄하라는 명령이 확인됐다는 뜻은 아니다. 패치 전 노출 시간을 줄이자는 조건부 대응 요청이다. 가용성을 지키기 위해 계속 열어 두는 것과, 정보를 보호하기 위해 잠시 닫는 것 사이의 판단이 경영 의제가 됐다는 점에서 인상적이다.

Node.js도 보안 업데이트: PHP와는 별개의 취약점이다

Node.js도 10월 21일 보안 업데이트를 발표했다. 같은 시기에 나왔다는 이유로 PHP 취약점이 Node.js로 번졌다고 해석하면 안 된다. 특히 주목할 항목은 Brotli 압축 해제기의 메모리 범위 밖 쓰기로 RCE가 가능해지는 CVE-2026-111497다. 공지는 제보자로 OpenAI Codex Security 연구진을 명시한다. 해당 압축 데이터를 처리하는 경로가 있는지 확인해야 하며 모든 Node 서버가 같은 방식으로 노출되는 것은 아니다.

다음은 Node.js 보안 공지의 10개 항목을 요약한 표다. 심각도는 그 공지의 분류를 따른다. TLS 두 건을 묶어 High로 적은 개별 릴리스 노트와 달리, 여기서는 CVE-2026-106072를 공지 본문대로 Medium으로 표시했다.

지원 종료 계열은 별도 이전이 필요하다. 위 버전은 이번 이슈의 수정 기준이며, 이후 추가 보안 공지가 나오면 해당 계열의 최신 지원 버전과 배포업체 공지를 다시 확인해야 한다.

운영자라면 먼저 이렇게 확인하겠다

나라면 스캐너부터 돌리기보다 실제 요청을 받는 런타임과 담당자부터 찾겠다. 개인 블로그도 호스팅 관리 영역과 직접 관리하는 컨테이너 영역이 나뉘기 때문이다.

  1. 공개 웹사이트·관리자 화면·잊힌 테스트 서버를 목록화하고 PHP·Node.js 사용 위치를 찾는다. 단순 정적 페이지 뒤에 별도 API가 있는지도 확인한다.
  2. 현재 실행 파일과 패키지·컨테이너 버전을 공식 수정판 및 공급업체 공지에 대조한다. 셸의 버전과 웹 서비스의 버전이 같은지 확인한다.
  3. 호환성 점검과 복구 준비 후 수정 패키지를 적용하고, 웹 프로세스를 재시작하거나 컨테이너를 재배포한다. 패치가 당장 어렵다면 외부 접근 제한을 검토한다.
  4. 다시 버전을 확인하고 로그인·업로드·예약 작업 등 주요 기능을 확인한다. WAF 규칙 적용만으로 런타임 패치를 끝낸 것으로 보지 않는다.
  5. 노출 기간의 오류·프로세스 실행·외부 연결·파일 변경을 점검한다. 침해가 의심되면 증거를 보존하며 격리하고, 비밀값 교체와 사고 대응을 진행한다.

순서의 근거는 PHP 공식 대응 안내와 KISA 대응 수칙다. 특히 침해 의심 서버는 재시작 전에 휘발성 증거를 확보해야 한다. 일반적인 패치 재시작과 사고 조사 시 증거 보존을 같은 순서로 처리하면 곤란하다.

운영 호스트나 해당 컨테이너 안에서 시작할 조회 명령 예시는 다음과 같다. 이 글에서 독자의 서버를 검사한 결과는 아니다.

php -v
node --version
node -p 'process.versions.brotli'

php -v는 CLI의 PHP일 수 있고, Node도 서비스 매니저나 컨테이너에서 다른 실행 파일을 사용할 수 있다. 관리자 확인을 위해 만든 phpinfo() 페이지를 인터넷에 공개해 두는 방식보다는 내부 관리 경로와 배포 기록을 확인하겠다.

Observatory의 높은 점수도 오래된 소프트웨어가 없다는 인증은 아니다. 이 점은 도구의 FAQ에도 명시돼 있다. 외부 헤더에서 PHP 버전이 안 보이거나 스캐너가 탐지하지 못했다는 사실보다, 실제 바이너리·패키지의 수정 여부를 더 신뢰하겠다.

더 나아가 이번 일을 계기로 서버 관리 기록을 남길 만하다. 어느 이미지와 패키지를 배포했고, 누가 재시작했으며, 어느 실행 프로세스에서 수정 버전을 확인했는지다. “업데이트했습니다” 한 줄보다 다음 담당자가 검증할 수 있는 기록이 오래 간다.
